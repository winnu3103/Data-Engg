The Complete Data Engineering Lifecycle

A comprehensive reference covering ingestion patterns, storage foundations, ACID/BASE/CAP, data modeling, SCD types, Medallion architecture, Data Vault 2.0, orchestration, DataOps, Data Products, and Enterprise Governance & Observability.

The Complete Data Engineering Lifecycle

A Data Engineer must understand the end-to-end journey of data — from its birth in a source system to its eventual archival. Every stage introduces risk; missing or mishandling any stage contributes to what is known as a Data Swamp.

Key Principle — Data as a Product: Data should be treated as a first-class asset at every stage: discoverable, trustworthy, governed, and well-understood — not just present in a table.
Stage 1 · Data Generation
Data originates from source systems. Types of sources:
  • OLTP Databases: ERP (SAP), CRM (Salesforce), e-commerce backends — high-frequency transactional writes.
  • IoT & Sensors: Machine telemetry, GPS, environmental sensors — high-volume, continuous streams.
  • SaaS APIs: REST / GraphQL APIs from third-party platforms (Hubspot, Stripe, Workday).
  • Event Streams: Clickstreams, user-behavior events published to message brokers.
  • Files: CSV uploads, EDI feeds, PDF exports, flat-file drops on SFTP.
Data formats: Structured (rows & columns) Semi-structured (JSON / XML / Avro) Unstructured (images / video / free text)
Stage 2 · Data Ingestion (Extract / Load)
Data is moved from sources into the data platform. Four main patterns:
  • Full Batch: Entire source table extracted on each run. Simple, but expensive at scale.
  • Incremental Batch: Only rows changed since the last run (using a watermark column). Far more efficient for large tables.
  • Streaming: Events flow in real-time via message brokers (Kafka, Kinesis). Millisecond latency, higher operational complexity.
  • CDC (Change Data Capture): Captures only INSERT / UPDATE / DELETE operations from the source system's transaction log — the gold standard for efficiency and completeness. See Tab 7 for a deep dive.
Stage 3 · Raw Storage (Landing Zone)
Data lands in a raw storage zone — a Data Lake (S3 / ADLS / GCS), a staging database, or an object store. The core rule: get it in, unchanged. File format choices (Parquet, Avro, JSON) made here have downstream performance and cost consequences. See Tab 2 for formats.
Stage 4 · Data Profiling & Discovery
Before building transformations, engineers statistically profile the data to understand its true state — not how it should look, but how it actually looks:
  • What percentage of each column is NULL?
  • What are the min / max / average values of numeric fields?
  • Are there duplicate rows based on a business key?
  • Do referential integrity constraints hold between tables?
  • Are there anomalous string lengths or outlier values?
Building pipelines without profiling is one of the most expensive mistakes in data engineering — assumptions made here haunt pipelines for years.
Stage 5 · Transformation & Processing (ELT / ETL)
Raw data is cleaned, standardized, enriched, and joined. Business rules (semantics) are applied here: deduplication, null handling, type casting, currency normalization, timezone standardization, code-table mapping. This is the ELT step in a modern Data Lakehouse (transform inside the warehouse using SQL / dbt).
Stage 6 · Data Modeling
Transformed data is restructured into a formal analytical model — Star Schema, Data Vault, 3NF, or One Big Table — optimized for the query patterns of its consumers. The model determines query speed, ease of understanding, and how well the data can answer historical questions. See Tabs 3–6.
Stage 7 · Orchestration & Scheduling
A pipeline scheduler (Apache Airflow, Prefect, Dagster) coordinates execution: ensuring Stage 5 does not run before Stage 4 completes, handling failures gracefully, retrying on transient errors, and sending SLA-breach alerts. Without orchestration, pipelines break silently — no one knows. See Tab 8.
Stage 8 · Serving & Data Products
Clean, modeled data is exposed to consumers as dashboards (Tableau, Power BI), SQL views, REST APIs, or ML training datasets. In a modern Data Mesh, these are packaged as formal Data Products with documented SLAs, ownership, and quality guarantees. See Tab 10.
Stage 9 · Data Quality & Observability (Continuous)
Automated testing and monitoring run on every pipeline execution to detect freshness failures, volume anomalies, schema changes, and accuracy degradation — before business users notice. This is not a one-time activity; it runs perpetually in production. See Tab 12.
Stage 10 · Governance, Compliance & Archiving
Tracking data lineage (where data came from and where it went), enforcing role-based access control (RBAC), applying classification labels (PII, PHI, PCI), ensuring regulatory compliance (GDPR, CCPA, HIPAA), and archiving cold data to cheaper storage tiers to reduce cost. See Tab 11.

The Data Contract — The Glue Between Stages

A Data Contract is a formal, versioned agreement between a data producer (the team generating data) and a data consumer (the team using it). It codifies:

  • Schema: Column names, data types, and nullability guarantees.
  • Semantics: What each field means in business terms.
  • SLA: Freshness guarantees — when data will be available and at what quality level.
  • Breaking Change Policy: How schema changes will be communicated, with advance notice and versioning.
Without Data Contracts: A source team can silently rename a column overnight and every downstream pipeline fails at midnight. Data Contracts are the contract-first discipline that prevents this class of failure entirely.

Storage & Database Foundations

1. Storage Types

Database (OLTP DB)

Organized storage for running applications. Row-based. Optimized for fast reads/writes of individual rows. Examples: PostgreSQL, MySQL, SQL Server, Oracle.

Data Warehouse (DWH)

Centralized repository for analytics and reporting. Columnar storage. Optimized for scanning millions of rows across few columns. Examples: Snowflake, BigQuery, Redshift.

Data Mart

A focused, department-specific subset of the Data Warehouse. Sales, Finance, and Marketing each get a purpose-built mart for faster, simpler queries scoped to their domain.

Data Lake

A vast pool of raw data in native formats (JSON, CSV, Parquet, images, video). Schema applied at query time ("schema on read"). Primary home for ML datasets and archival.

Data Lakehouse ⭐

A modern hybrid: raw files stored in a Data Lake (S3 / ADLS / GCS) but accessed with Data Warehouse capabilities — ACID transactions, SQL, indexing, schema enforcement — via open table formats (Delta Lake, Apache Iceberg).

Operational Data Store (ODS)

A near-real-time integration layer holding the current state of operational data integrated from multiple source systems. Designed for current-state queries, not deep historical analytics.

2. Row-Oriented vs. Columnar Storage

Dimension Row-Oriented (OLTP) Columnar (OLAP)
Physical layout All columns of one row are stored together on disk: (id=1, name='Alice', age=30) → (id=2, name='Bob', age=25) Each column stored together: all IDs, then all names, then all ages
Best for Reading or writing a single row quickly. INSERT / UPDATE / DELETE transactions. Aggregating a single column across millions of rows: SELECT SUM(revenue) …
Compression Poor — each "chunk" is heterogeneous (mixed types), compresses badly. Excellent — homogeneous column data (all integers, all dates) compresses 5–10×.
I/O efficiency Must read every column even if only one is needed. Only reads columns referenced in the query — "column pruning."
Examples PostgreSQL, MySQL, Oracle, SQL Server Snowflake, BigQuery, Redshift, Apache Parquet files

3. OLTP vs. OLAP vs. HTAP

Purpose Run the business (app backends, e-commerce) Analyze the business (BI, dashboards, reporting) Both simultaneously on one platform

4. ACID Properties (Critical for OLTP)

ACID guarantees that a database transaction — like a bank transfer — is processed reliably even under hardware failure or concurrent access:

  • Atomicity: "All or nothing." A transaction has 5 steps; if step 4 fails, all previous steps roll back automatically. No partial state is ever persisted.
  • Consistency: A transaction must bring the database from one valid state to another. All constraints, rules, and cascades must pass — otherwise the entire transaction is rejected.
  • Isolation: Concurrent transactions execute as if they were sequential. Multiple transactions at the same millisecond do not see each other's in-flight changes. Isolation levels (Read Uncommitted → Read Committed → Repeatable Read → Serializable) control the trade-off between concurrency and correctness.
  • Durability: Once a transaction is committed, it survives system crashes. Achieved via Write-Ahead Logging (WAL): changes are written to a durable log before being applied to data files.

5. BASE Properties (Distributed / NoSQL Systems)

Distributed NoSQL systems (Cassandra, DynamoDB, CouchDB) trade full ACID consistency for extreme scalability and availability using BASE semantics:

  • Basically Available: The system guarantees availability even if some nodes are unreachable. Reads and writes always get a response (possibly stale).
  • Soft State: The system's state may change over time even without new writes, as eventual consistency propagation continues in the background.
  • Eventually Consistent: Given enough time with no new writes, all replicas will converge to the same value. At any instant, replicas may disagree.
ACID vs. BASE trade-off: Use ACID (RDBMS) when correctness is non-negotiable (financial transactions, inventory). Use BASE (NoSQL) when scale and availability matter more than strict consistency (social media feeds, shopping carts).

6. The CAP Theorem

In any distributed database system, you can guarantee at most 2 of these 3 properties simultaneously:

Consistency (C)

Every read returns the most recent write or an error. All nodes see identical data at the same instant.

Availability (A)

Every request receives a response (not an error), though the data returned may not be the most recent write.

Partition Tolerance (P)

The system continues to operate even when network messages between nodes are dropped (a "network partition").

Practical implication: Network partitions are unavoidable in real distributed systems, so P is non-negotiable. The real design choice is:

  • CP systems (Consistent + Partition Tolerant): Will refuse to respond rather than return stale data. Examples: HBase, Zookeeper, MongoDB (with majority read concern).
  • AP systems (Available + Partition Tolerant): Will return a response even if it may be slightly stale. Examples: DynamoDB, Cassandra, CouchDB.

7. File Formats in the Data Lake

Format Storage Model Best For Key Characteristics
CSV Row-based, text Simple exports, human-readable hand-offs No embedded schema. No compression. Universally supported. Terrible for analytics at scale. No support for nested data.
JSON / JSONL Row-based, text API responses, semi-structured data Flexible schema. No compression. Verbose. JSONL (one JSON object per line) is streaming-friendly and easy to append.
Avro Row-based, binary Event streaming, schema evolution Schema embedded in every file. Built for Kafka. Excellent schema evolution (backward / forward compatible via Schema Registry). Compact binary encoding.
Parquet Columnar, binary Analytics at scale — the de facto standard Industry standard for data lakes. Excellent compression (Snappy, Zstd). Supports predicate pushdown (skip irrelevant row groups without reading them). Supports nested structures. Best choice for OLAP workloads on S3.
ORC Columnar, binary Hive / Hadoop ecosystems Similar to Parquet. Historically better performance in Hive. Less prevalent in modern Spark / Snowflake / Databricks stacks.
Delta Lake Columnar + transaction log Lakehouse — ACID on the data lake Parquet files + a JSON transaction log. Adds ACID transactions, time travel, upserts (MERGE), schema enforcement, and schema evolution to raw data lake files. Created by Databricks. Open-sourced in 2019.
Apache Iceberg Columnar + metadata layer Multi-engine Lakehouse standard Open table format specification (not a storage engine). Supports ACID, partition evolution (change partitioning without rewriting data), schema evolution, and time travel. Natively supported by Spark, Trino, Flink, Snowflake, and AWS Athena. The emerging cross-cloud open standard.

8. Partitioning & Clustering

Two critical performance techniques for large-scale tables:

  • Partitioning: Data is physically split into separate files or folders by a column value (e.g., year=2024/month=06/day=08/). A query filtered to a specific date only scans that date's partition — called partition pruning. Choose partition columns that appear in WHERE clauses.
  • Clustering / Micro-partitioning (Snowflake): Within partitions, data is sorted by a secondary key so similar values are co-located. Enables Snowflake to skip irrelevant micro-partitions for range-based queries without a full scan.
Small File Problem: Over-partitioning creates millions of tiny files, which is catastrophically slow for file-system-based engines (Spark, Hive). Use compaction / optimize jobs (Delta OPTIMIZE, Iceberg rewrite_data_files) to periodically merge small files back into large ones.

9. MPP Architecture (Massively Parallel Processing)

Modern Data Warehouses (Snowflake, BigQuery, Redshift) use MPP to distribute a single query across hundreds of compute nodes simultaneously. A query like SELECT SUM(revenue) FROM Fact_Sales is split into parallel subtasks — each node scans a slice of data and returns a partial sum — then the coordinator merges the results. This is why columnar warehouses can scan billions of rows in seconds. Crucially, in Snowflake the compute (Virtual Warehouse) and storage (S3) are decoupled — you scale each independently.

Data Modeling: 3NF, Kimball, Snowflake Schema & Beyond

1. 3rd Normal Form (3NF) — The Inmon Approach

Normalization breaks data into many small tables to eliminate redundancy. The three normal forms build on each other:

  • 1NF: Each column is atomic — no repeating groups, no multi-valued cells, no arrays in a single field.
  • 2NF: Every non-key attribute depends on the entire primary key (eliminates partial dependencies, relevant only when primary key is composite).
  • 3NF: Every non-key attribute depends only on the primary key — not on other non-key attributes (eliminates transitive dependencies).
  • Pros: Zero data duplication. Single update point (update a State name in 1 row — propagates everywhere). Perfect data integrity.
  • Cons: Terrible for analytics. "Total Sales by State" requires a 4-table JOIN — slow and complex for BI tools. Used in the Silver / ODS layer, not the Gold / reporting layer.

2. Dimensional Modeling — The Kimball Star Schema

Ralph Kimball's approach: denormalize data to optimize for read-heavy analytical queries.

Step 0: Define the Grain (The Most Critical Concept)

The grain is the precise definition of what a single row in a Fact table represents. You must define the grain before choosing any columns.

  • Good "One row = one line item on one sales order, at one store, on one day."
  • Bad "One row = something about a sale." — Ambiguous grain leads to double-counting aggregations.
Grain Rule: Once the grain is defined, every Fact table column must either be a measurement at that grain or a foreign key to a dimension at that grain. Never mix grains in one Fact table.

Types of Fact Tables

Type Grain How rows are added Example
Transaction Fact One row per discrete business event. Appended as events occur. Can grow to billions of rows. Each individual sales transaction, each web click, each invoice line item.
Periodic Snapshot Fact One row per time period, capturing cumulative state at that point. Rows inserted on a schedule (daily, monthly) — even if nothing changed. Daily end-of-day inventory count. Monthly account balance snapshot.
Accumulating Snapshot Fact One row per business process instance, tracking progress through milestones. Row is updated as the process advances through stages. Rare for fact tables to be updated — this is a deliberate design. One row per order: columns for Placed_Date, Shipped_Date, Delivered_Date, Returned_Date — each filled in as the milestone is reached.

Types of Measures (Facts)

  • Additive: Can be summed meaningfully across all dimensions (time, geography, product). The most useful. Example: Sales_Amount, Units_Sold.
  • Semi-Additive: Can be summed across some dimensions but not across time. Example: Account_Balance — summing daily balances for a month gives a meaningless number; you want the period-end balance. Use MAX() or snapshot logic instead of SUM() for the time dimension.
  • Non-Additive: Cannot be summed at all. Must use COUNT, AVG, or derived ratios. Example: Profit_Margin_Pct, Customer_Satisfaction_Score, Unit_Price.

Special Dimension Types

Type Description Example
Conformed Dimension A dimension shared identically across multiple Fact tables. Enables "drill-across" queries — joining two unrelated Fact tables through their shared dimension. Dim_Date and Dim_Customer used by both Fact_Sales and Fact_Returns. Shared dimensions allow comparing Sales vs. Returns by Customer in a single query.
Junk Dimension A single table holding multiple low-cardinality flags and indicators to reduce Fact table width. Contains all combinations of the flags. Instead of 10 boolean columns in Fact_Sales (is_promotion, is_return, is_rush_order, is_online…), combine them into Dim_Transaction_Flags with one surrogate key.
Degenerate Dimension A dimension attribute that lives directly in the Fact table — no corresponding Dimension table exists because there are no descriptive attributes worth a separate table. Invoice_Number, Order_Number in Fact_Sales. It's a dimension conceptually (you filter by it), but it holds no further descriptive data.
Role-Playing Dimension A single physical dimension table used multiple times in one Fact table under different aliases. Dim_Date used three times in Fact_Orders: as Order_Date_Key, Ship_Date_Key, and Delivery_Date_Key. Each alias is a separate SQL view of the same physical table.
Outrigger Dimension A secondary dimension that is attached to a primary dimension (not directly to the Fact table). Rare — used when a dimension attribute itself has its own dimension. Dim_Customer contains a Salesperson_Key that points to Dim_Salesperson. The Salesperson outriggers off Customer, not off the Fact.

Surrogate Keys vs. Natural Keys

A Surrogate Key is a system-generated meaningless integer (1, 2, 3…) used as the primary key of Dimension tables, replacing the natural source-system key.

  • Why: Natural keys can change, be reused by source systems, or be inconsistent across systems. Surrogate keys are stable, compact (integer joins are faster than string joins), and enable SCD Type 2 (multiple rows per entity).
  • Rule: Always join Fact tables to Dimensions via Surrogate Keys. Never expose surrogate keys to business users — they carry no business meaning.

3. The Snowflake Schema

A normalized variant of the Star Schema where Dimension tables are further decomposed (e.g., Dim_Customer → Dim_City → Dim_State → Dim_Country). Saves disk space but adds JOIN complexity. Generally avoided in modern columnar warehouses where storage is cheap but query JOINs cost compute.

4. One Big Table (OBT)

A modern pattern used in some Data Lakehouses. All dimension attributes are pre-joined into a single wide flat table — eliminating JOINs entirely at query time.

  • Pros: Extremely fast for BI tools (zero joins). Simple enough for non-technical SQL writers.
  • Cons: Massive data duplication. Updates are expensive. Only feasible with columnar compression (Parquet / Snowflake). Cannot represent complex many-to-many relationships cleanly.
  • Best for: Self-service analytics platforms, embedded analytics, and scenarios where read latency is the only priority.

Deep Dive: Slowly Changing Dimensions (SCDs)

When a descriptive attribute in a Dimension changes over time (a customer moves cities, an employee changes job titles, a product changes categories), you must decide how the data warehouse handles that change. The SCD framework provides standardized strategies for each scenario.

Why this matters critically: If you use SCD Type 1 (overwrite) for a Sales Territory dimension, all historical sales will be re-attributed to the current territory — not the territory at the time of the sale. This silently corrupts historical analysis without any error messages.

The Surrogate Key Foundation

All SCD implementations depend on Surrogate Keys — system-generated integer IDs independent of the business key. This allows multiple rows to coexist for the same entity (as in Type 2) without natural key conflicts.

Type Strategy When to Use Example Result Key Tradeoffs
Type 0
Retain Original		 Ignore all changes. The first value loaded is permanent. Immutable facts: Date of Birth, Original Sign-Up Date, Contract Start Date. John registered from NY in 2018. Even after moving to CA, the record still shows NY. ✅ Simplest possible. ❌ Wrong if the attribute should reflect the current state.
Type 1
Overwrite		 Update the existing row in-place. Old value is permanently deleted. Correcting data quality errors. Fields where history is irrelevant: Phone Number, Email, Typo corrections. Row: City updated from NY → CA. NY is gone forever from the DWH. ✅ Simple, small table. ❌ Zero historical tracking. Point-in-time analysis is impossible.
Type 2
Add New Row ⭐		 Expire the current row (set Effective_End_Date, Is_Current = 0). Insert a brand-new row with the new value. Both rows share the same Natural Key but have different Surrogate Keys. Any time you need full historical tracking for point-in-time reporting. Sales Territory, Employee Department, Customer Segment, Product Category. Row 1: John | NY | Start=2020-01-01 | End=2025-06-01 | Is_Current=0
Row 2: John | CA | Start=2025-06-01 | End=NULL | Is_Current=1		 ✅ Complete history preserved. Full point-in-time analysis enabled. ❌ Table grows with every change. Queries must filter on Is_Current or date range.
Type 3
Add New Column		 Add a Previous_Value column to the existing row. Only one level of history is stored. When you only need the immediately preceding value: before/after org restructuring, recent address change. John | Current_City=CA | Previous_City=NY. (TX, the city before NY, is lost.) ✅ Single row per entity — simple table. ❌ Loses any history beyond one change back.
Type 4
History Table		 Maintain a Type 1 (always-current) main dimension. Route all changes to a separate Dim_X_History table that stores every version. Rapidly changing dimensions where the main table must stay lean and fast, but full history must be retained. Main: John | CA (always current). History: (John|NY|2018), (John|TX|2021), (John|CA|2025). ✅ Fast current lookups. Full history available. ❌ Requires JOINs to history table for any retrospective analysis.
Type 6
Hybrid (1+2+3) ⭐		 Combines all three types. Uses Type 2 new-row insert (full history), Type 1 "current value" column that is updated across ALL rows for the entity, and Type 3 "previous value" column on each row. When you need full historical accuracy AND easy access to the current value without additional joins on every query. Row 1: John | City_At_Time=NY | Current_City=CA | Prior_City=NY | Is_Current=0
Row 2: John | City_At_Time=CA | Current_City=CA | Prior_City=NY | Is_Current=1		 ✅ Maximum flexibility. Historical rows carry the current value, enabling "current state + history" in one query. ❌ Most complex to implement and maintain. Requires updating Current_City on all prior rows on every change.

Standard SCD Type 2 Column Pattern

  • Surrogate_Key — Integer primary key. Auto-increments per row, not per entity.
  • Natural_Key — The original business identifier (e.g., Customer_ID from the source system).
  • Effective_Start_Date — When this version became active.
  • Effective_End_Date — When this version expired. NULL = still current.
  • Is_Current_Flag — Boolean. 1 = active record. Used for fast "current state" queries without date math.
  • Record_Source — Which source system provided this version.
  • Hash_Diff — A hash of all attribute columns. Used to detect changes efficiently without column-by-column comparison on large dimension tables.

Point-in-Time Query Pattern (Type 2)

To find which region a customer belonged to on a specific historical date:

SELECT *
FROM   Dim_Customer
WHERE  Natural_Key           = 'CUST_123'
  AND  Effective_Start_Date <= '2023-06-15'
  AND  (Effective_End_Date   >  '2023-06-15'
        OR Effective_End_Date IS NULL);

dbt Snapshots — Type 2 Automation

In dbt, SCD Type 2 is implemented via the dbt snapshot feature. You define a snapshot in a snapshots/ directory with:

  • strategy: timestamp — Uses an updated_at column to detect changes (efficient).
  • strategy: check — Compares specified columns row-by-row (works when no updated_at exists, but slower).

dbt automatically manages dbt_scd_id, dbt_valid_from, dbt_valid_to, and dbt_updated_at columns on every snapshot run.

The Medallion Architecture (Bronze → Silver → Gold)

The Medallion architecture (popularized by Databricks) is a multi-hop data pipeline pattern that guarantees data becomes progressively cleaner, more structured, and more valuable as it moves "right" through the layers. It is the standard organizing principle for Data Lakehouses.

Schema on Read vs. Schema on Write

Concept Schema on Write (Data Warehouse) Schema on Read (Data Lake)
When is schema enforced At write time — data is rejected if it doesn't match the defined schema. At read / query time — raw data is stored as-is; the reader applies the schema.
Data quality guarantee Strong — only conforming data can land. None — inconsistent data can silently fail at query time.
Flexibility Lower — schema changes require migration scripts. Higher — any shape of data can be stored immediately.
Where used in Medallion Silver and Gold layers (enforced schema). Bronze layer (raw landing, any format accepted).

🥉 Bronze Layer — Raw / Landing

Goal: Ingest safely. Preserve everything. Never transform.

  • Data lands exactly as it arrives from source — no column renaming, no type casting, no filtering.
  • If any downstream pipeline fails, Bronze is the replay point. It is your immutable audit trail.
  • Standard metadata columns are appended at load time: _ingestion_timestamp, _source_system, _file_name, _batch_id.
  • Stored as Parquet / Delta / Iceberg files in S3 / ADLS / GCS.
  • Schema on read applies here — accept any shape from the source.
  • Enterprise naming: STG (Staging), RAW, or Landing Zone.
Bronze Rule: Never delete Bronze data. It is the time machine that enables full pipeline reruns and incident investigation.

🥈 Silver Layer — Cleaned / Conformed / Validated

Goal: Establish the Enterprise Source of Truth for the current state of business entities.

  • Deduplication: Remove exact duplicates; resolve soft duplicates via business key logic.
  • Type enforcement: Cast strings to dates, decimals, booleans. Reject or quarantine non-conforming rows.
  • Standardization: Convert timezones to UTC, normalize currency codes, apply code-table mappings (status codes → human labels).
  • Null handling: Coalesce nulls where appropriate; flag rows where mandatory fields are missing.
  • Data organized around business entities: Customers, Orders, Products, Invoices, Employees.
  • Schema on write enforced here — schema contracts applied.
  • Represents the "current state" of each entity; history may be partially tracked.
  • Enterprise naming: ODS (Operational Data Store) or CDM (Common Data Model).

🥇 Gold Layer — Curated / Business-Ready

Goal: Answer specific business questions fast, at the level of abstraction business users think in.

  • Data structured into Star Schemas (Fact + Dimension tables) or One Big Tables for BI tools.
  • Full historical tracking via SCD Type 2 on Dimension tables.
  • Pre-aggregated summary tables for common metrics (daily/monthly/YTD totals).
  • ML feature stores and versioned training datasets.
  • Formal Data Products with SLAs, ownership, and catalog registration.
  • Enterprise naming: Core DW, Aggregates, CURATED layer, Data Products.

Delta Lake & Apache Iceberg — ACID on the Data Lake

These open table formats add Data Warehouse-grade capabilities to raw files in object storage:

Time Travel ✅ SELECT … VERSION AS OF 10 or TIMESTAMP AS OF '2024-01-01' ✅ Query by snapshot ID or timestamp
Schema Evolution ✅ Add / rename / drop columns without rewriting data ✅ Full schema evolution with backward compatibility options
Partition Evolution ❌ Limited — changing partition strategy requires a rewrite ✅ Change partitioning strategy on existing data without rewriting files
Upserts (MERGE / UPSERT) ✅ Full MERGE INTO support ✅ Full MERGE support

Streaming in the Medallion Architecture

  • Bronze (Streaming Landing): Kafka / Kinesis events write directly to Bronze as raw messages — append-only, millisecond latency. Often stored as JSONL or Avro for schema evolution.
  • Silver (Stateful Deduplication): Streaming deduplication using watermarks — the engine waits up to N hours for late-arriving events before closing a time window. State is maintained in a persistent state store (RocksDB in Flink / Spark).
  • Gold (Micro-batch Aggregation): Gold-level aggregations (hourly KPIs, rolling 7-day metrics) typically run as micro-batch (every 5–15 minutes) — balancing business latency requirements against compute cost.
Event Time vs. Processing Time: Always use event time (when the event happened in the source system) for windowed aggregations, never processing time (when your pipeline received it). A 5-minute network delay should not misattribute a purchase to the wrong time window.

Multi-Hop Patterns

The three layer names are logical. In practice, pipelines can have multiple hops within a layer:

Bronze_Raw → Bronze_Validated → Silver_Integrated → Silver_Enriched → Gold_Dimensional → Gold_Aggregated

Each hop is a separate dbt model or Spark job with its own tests and lineage. The key principle: each hop adds exactly one type of transformation — never mix cleaning + enriching + modeling in a single step.

Data Vault 2.0 — Deep Dive

Data Vault 2.0 (DV2) is an advanced Silver-layer modeling methodology designed for large enterprises with many source systems, frequent schema changes, and strict audit / compliance requirements. It is fully insert-only, parallelizable, and designed to be rebuilt from scratch if needed.

When NOT to use Data Vault: Small teams, 1–2 source systems, projects needing fast time-to-insight. DV2's upfront modeling overhead pays off only when you have 5+ source systems feeding the same business entities, and schema changes arrive frequently.

Why Data Vault Over 3NF or Kimball?

  • Agility: Adding a new source system = adding new Satellites or Links. Core Hub definitions never change. In 3NF, a schema change in one source can cascade into breaking changes across many joined tables.
  • Auditability: Every single row in every table carries a Load_Date and Record_Source. Full provenance of every data point is maintained.
  • Parallel Loading: Hubs, Links, and Satellites have no foreign key dependencies on each other at load time, so all three component types can be loaded simultaneously from the same source batch.
  • No Updates: Insert-only design means no locking contention. Historical data is never overwritten — only new rows are added.

The 6 Data Vault Components

Component Contains Key Rule Columns Example
Hub The unique business key for a core enterprise entity. Nothing else — no descriptions, no attributes. One row per unique business key. Immutable — never updated, never deleted. The "spine" of the vault. HUB_CUSTOMER: Hash_Key, Customer_ID, Load_Date, Record_Source
Link The relationship between two or more Hubs. Contains only their Hash Keys — no attributes. Insert-only. Relationships are facts. If a business relationship changes, a new Link is added — not updated. LNK_ORDER_PRODUCT: Hash_Key, Order_HK, Product_HK, Load_Date, Record_Source
Satellite Descriptive attributes for a Hub or Link — everything that changes over time (names, addresses, status, amounts). Strictly insert-only. Every attribute change creates a new row with a new Load_Date. Provides an unalterable, audit-grade change history. SAT_CUSTOMER_DETAILS: Customer_HK, Load_Date, Load_End_Date, First_Name, City, Email, Hash_Diff, Record_Source
Reference Table (REF) Shared enterprise lookup / code tables. Not owned by any single Hub. Shared across the entire vault. Versioned like Satellites when codes change. REF_CURRENCY: Currency_Code, Currency_Name, Symbol, Load_Date
Point-in-Time (PIT) A performance optimization table — a pre-computed snapshot of Satellite Load_Dates for each business key at each calendar date. Eliminates complex MAX(Load_Date) subqueries on Satellites at query time. Rebuilt periodically or incrementally. Customer_HK | Snapshot_Date | SAT_DETAILS_Load_Date | SAT_ADDRESS_Load_Date | SAT_FINANCIALS_Load_Date
Bridge Table A pre-joined, flattened view of multiple related Links for reporting performance. Built for specific reporting use cases. Rebuilt when Links change. Avoids runtime multi-hop join chains. Flattens Customer → Orders → Products → Invoices into one denormalized key structure for Gold layer consumption.

Mandatory Metadata Columns (DV2 Standards)

Every single Data Vault table — Hub, Link, and Satellite — must carry these four columns:

  • HASH_KEY: A deterministic hash (MD5 or SHA-256) of the business key. Used as the primary key. Ensures consistent joins across any source system. Must be computed identically across all loading processes.
  • LOAD_DATE (LDTS): The exact timestamp when this record was loaded into the vault by the ETL process. Never the source system's own timestamp (that goes in a Satellite). This enables replaying the vault from any point in time.
  • RECORD_SOURCE (RSRC): The source system that provided this record (e.g., 'SALESFORCE.ACCOUNT', 'SAP.VBAP'). Critical for root-cause debugging.
  • HASH_DIFF (Satellites only): A hash of all attribute column values concatenated. Compared to the last loaded row to detect changes — far faster than column-by-column comparison on wide Satellites.

Raw Vault vs. Business Vault

Dimension Raw Vault Business Vault
Contains Source data loaded as-is. No business rules applied. Pure capture of every source record. Derived or calculated data applying business logic. Soft rules only.
Rules applied Hard rules only: structural normalization (type casting, business key extraction, hash computation). Soft rules: "Active Customer" definition, currency conversion, revenue classification, derived metrics.
Changes when Only when the source system's structure changes. The raw vault is as stable as the source. When business definitions or rules change. Can be fully rebuilt from Raw Vault data without re-ingesting from source.

Ingestion Patterns & CDC

Ingestion is the first critical step: moving data from source systems into the data platform. The pattern chosen determines cost, latency, complexity, data completeness, and downstream correctness.

1. The Four Core Ingestion Patterns

Pattern Description Latency Best For Tools
Full Extract (Batch) Entire source table extracted on every run. Simple but inefficient — reads data that hasn't changed. Hours (usually nightly) Small, stable reference tables. Simple first-pass pipelines. SQL CTAS, Fivetran full sync, nightly CSV export
Incremental Batch Extract only rows modified since the last run, using a high-watermark column (updated_at > last_run_time) or sequence number. Minutes to hours Large OLTP tables where full extract is cost-prohibitive. dbt incremental models, Airbyte, Fivetran incremental
Streaming Events are published to a distributed message broker as they occur and consumed in real-time. True event-driven architecture. Milliseconds to seconds Clickstreams, IoT telemetry, fraud detection, live operational dashboards. Apache Kafka, AWS Kinesis, Google Pub/Sub, Azure Event Hubs
Micro-batch Batch processing in small, frequent time windows (every 1–15 minutes). Simulates streaming with simpler batch-oriented semantics. 1–15 minutes Near-real-time use cases without the full operational complexity of pure streaming. Spark Structured Streaming, AWS Glue with triggers, Databricks Auto Loader

2. CDC (Change Data Capture) — Deep Dive

CDC captures only the rows that changed (INSERTs, UPDATEs, DELETEs) in a source system since the last extraction. It is the gold standard for incremental ingestion because it captures all operation types including hard deletes — something watermark-based incremental batch cannot do.

CDC Approaches Compared

Approach How It Works Pros Cons
Log-Based CDC ⭐ Reads the database's transaction log directly (PostgreSQL WAL, MySQL binlog, SQL Server CDC, Oracle Redo Log). Captures all operations without running any queries on the source DB. Zero load on source DB. Captures DELETEs. Sub-second latency possible. Exact replication of every change. Requires privileged DB access (replication role). Log format varies by vendor. Must monitor log retention to avoid gaps.
Query-Based CDC Polls the source DB with a query filtered by a timestamp or sequence column: WHERE updated_at > :last_watermark. Simple to implement. Works on any database with no special permissions. Adds query load to source DB (can impact application performance). Cannot capture DELETEs. Fails silently if rows lack an updated_at column or it isn't indexed.
Trigger-Based CDC Database triggers fire on INSERT / UPDATE / DELETE and write changes to a shadow / audit table. Captures all operation types including DELETEs. No external tooling. Doubles write load on the source DB. Triggers are fragile and hard to maintain at scale. Risk of impacting source application performance.

Popular CDC Tools: Debezium (open-source, log-based), AWS Database Migration Service (DMS), Fivetran, Airbyte, Striim, Confluent Platform.

3. Pull vs. Push Ingestion

Model Description Example Consideration
Pull (Scheduled / Polled) The data platform initiates the extract from the source on a schedule. Airflow DAG runs at midnight and queries the source OLTP DB. Simple to control. Depends on source system availability at the scheduled time.
Push (Event-Driven) The source system sends data to the platform when events occur — no polling needed. A webhook fires when a new order is placed; data lands in Kinesis within milliseconds. Lower latency. Source system must be capable of publishing events. Requires a message broker or API endpoint.

4. Idempotency — Non-Negotiable for Reliable Pipelines

Idempotency means: running the same pipeline with the same inputs multiple times always produces the same result — no duplicate rows, no data loss.

Why it matters: Pipelines fail and must be retried. A non-idempotent pipeline will duplicate data every time it is retried. A pipeline that has run 5 times should look identical to one that ran once.
  • Use MERGE / UPSERT instead of raw INSERT when loading into structured tables.
  • Use a deduplication step (GROUP BY business key) at the Bronze → Silver boundary.
  • Track watermarks in a persistent control table, not in pipeline memory (which is lost on restart).
  • Design each pipeline step to be a pure function: same input → same output, regardless of how many times it runs.

5. Late-Arriving Data & Watermarks (Streaming)

In streaming systems, events do not always arrive in order. A transaction that occurred at 11:58 PM may not reach your Kafka consumer until 12:04 AM the next day due to network delays.

  • Watermark: A threshold telling the streaming engine how long to wait for late events before closing (finalizing) a time window. Example: "Close the 11:00–12:00 PM window at 2:00 PM — wait 2 hours for late arrivals."
  • Event Time vs. Processing Time: Always aggregate on event time (when the event occurred in the source) rather than processing time (when your consumer received it). Network jitter should not misattribute a purchase to the wrong day's metrics.
  • Allowed Lateness: After the watermark passes, some engines (Apache Flink) can still accept "allowed late" events and emit result corrections for a configurable period.

6. Ingestion Considerations by Source Type

Source Type Key Engineering Considerations
REST API Handle pagination (cursor-based preferred over offset-based for large datasets). Respect rate limits — implement exponential backoff on 429 / 503 responses. Always store the raw API response in Bronze before parsing — API schemas change without warning.
File Drop (S3 / SFTP) Handle encoding issues (UTF-8 vs Latin-1). Varying delimiters and extra header rows. Move processed files to an "archived/" prefix, never delete them. Validate file completeness with row counts or checksums if provided by the sender.
Database (JDBC) Use read replicas to avoid impacting the production OLTP system. Set query timeouts. Use JDBC partitioning (partition by a numeric column) for parallel extraction of large tables.
Kafka / Event Stream Choose the right delivery semantic: at-most-once (fast, may lose), at-least-once (may duplicate — handle with dedup), exactly-once (slowest, guaranteed). Use a Schema Registry (Confluent / AWS Glue) to manage Avro / Protobuf schema evolution across producers and consumers.

Orchestration & DataOps

Orchestration coordinates pipeline execution: what runs, in what order, when, and what happens on failure. Without orchestration, pipelines are isolated scripts with no visibility, no retry logic, and no guarantees.

1. Core Orchestration Concepts

DAG (Directed Acyclic Graph)

The pipeline blueprint. A collection of tasks linked by dependencies. "Directed" means tasks have order. "Acyclic" means no circular dependencies — Task A cannot wait on Task B if B waits on A.

Task

The smallest unit of work — a Python function, SQL statement, bash command, or API call. Each task has its own status: queued, running, success, failed, skipped.

Dependency

A task only starts after all upstream tasks succeed. In Airflow: extract >> transform >> load. Forms the execution order graph.

Schedule

A cron expression or event trigger controlling when a DAG runs. Example: 0 6 * * * = 6:00 AM every day. Can also be triggered by events (file arrival, API call).

Sensor

A special task that waits for an external condition before proceeding: wait for a file in S3, wait for a Snowflake table to update, wait for a Kafka topic to have new messages. Far better than sleep() calls.

Backfill

Re-running a DAG for historical dates to populate missing or incorrect data. Requires pipelines to be idempotent. Critical for incident recovery and retroactive data corrections.

SLA (in Airflow)

A time threshold by which a task or DAG must complete. If missed, Airflow can send email/Slack alerts. Different from a Data Product SLA — this is pipeline-level timing.

Retry with Backoff

Automatically retry failed tasks with increasing delay between attempts (e.g., 1 min → 2 min → 4 min). Handles transient failures (network timeouts, API rate limits) without human intervention.

2. Apache Airflow Architecture

Component Role
Scheduler The brain. Continuously monitors DAG files, determines which tasks are ready to run based on dependencies and schedule, and submits them to the Executor.
Executor Controls how tasks actually run. LocalExecutor (single machine, parallel threads), CeleryExecutor (distributed workers via a message broker), KubernetesExecutor (each task gets its own isolated Pod — best for diverse Python environments).
Webserver The UI: view DAG runs, task logs, dependency graphs, trigger manual runs, and manage connections & variables.
Metadata Database A PostgreSQL / MySQL database storing all DAG definitions, task instance states, run history, XComs, connections, and variables. The operational state of the entire system lives here.
Workers The processes (or Pods) that actually execute task code. Stateless — can be scaled horizontally.

Key Airflow Operators

  • PythonOperator — Execute a Python callable.
  • BashOperator — Run a shell command.
  • SnowflakeOperator — Execute a SQL statement on Snowflake via a Connection.
  • S3KeySensor — Wait for a specific S3 key to exist.
  • DbtRunOperator / DbtTestOperator — Trigger dbt models and tests.
  • TriggerDagRunOperator — Trigger another DAG from within a DAG (pipeline chaining).
  • ShortCircuitOperator — Conditionally skip downstream tasks based on runtime logic (e.g., skip Gold rebuild if no new Silver data arrived).

4. DataOps Principles

DataOps applies DevOps engineering discipline to data pipelines — emphasizing automation, collaboration, monitoring, and rapid iteration:

  1. Automated Testing: Every pipeline change triggers automated schema tests, row-count checks, and business rule validations before the code is deployed to production.
  2. CI/CD for Data Pipelines: All changes go through Pull Request review → automated testing on a dev schema → staged deployment (DEV → QA → PROD).
  3. Version Control Everything: SQL models, Python scripts, DAG definitions, infrastructure (Terraform), and configuration are all in Git. No "hero scripts" on someone's laptop.
  4. Monitoring & Alerting: Pipeline failures, quality degradations, and SLA breaches trigger automatic alerts to the responsible team — not discovered by an angry business user on a Monday morning.
  5. Shift-Left Quality: Catch data quality issues as early as possible — at Bronze ingestion — not after they have propagated to Gold layer dashboards where they are expensive to fix.
  6. Fast Feedback Loops: Slim down local development cycles. Engineers should be able to run a pipeline end-to-end on a sample dataset in minutes, not hours.
  7. Modular Design: Each pipeline stage is independently deployable and testable. A failure in the Gold layer should not prevent the Silver layer from updating.

Operations, Data Mesh & CI/CD for Data

1. Centralized vs. Decentralized — Data Mesh

In a centralized model, a single platform team owns all data engineering for the entire company. As the company scales, this team becomes a permanent bottleneck — every new report requires a ticket. Data Mesh solves this structurally.

The 4 Principles of Data Mesh (Zhamak Dehghani)

1. Domain Ownership

Data is owned and managed by the business domain that generates it. The Sales domain owns Sales data. Finance owns Finance data. Each domain has its own embedded data engineers. Data is co-located with the teams that understand it best.

2. Data as a Product

Each domain treats its data outputs as formal products — not just tables. Products are discoverable, reliable, documented, versioned, and supported. Domains are accountable for quality and SLAs.

3. Self-Serve Data Platform

A central Platform Team provides shared infrastructure — provisioned Snowflake environments, dbt project templates, Airflow instances, CI/CD pipelines, catalog tooling. Domain teams consume this platform to stay autonomous without reinventing the wheel.

4. Federated Computational Governance

Global standards are defined centrally (PII classification, interoperability formats, security policies) but enforced computationally at the domain level (via automated CI checks, policy-as-code). Avoids both chaos (no governance) and bottleneck (central approval for everything).
Data Mesh is an organizational and architectural paradigm, not a technology. You can implement Data Mesh on Snowflake + dbt + Airflow. The shift is in ownership, accountability, and how teams are structured — not which tools you use.

2. ETL vs. ELT

Dimension ETL (Extract, Transform, Load) ELT (Extract, Load, Transform)
Where transform happens In a dedicated ETL server / middleware before loading into the DWH. Raw data loads into the DWH first; transformation runs inside the DWH using SQL.
Raw data preserved? No — only transformed data lands in the warehouse. Raw is discarded. Yes — raw data always preserved in Bronze. Full re-transformation is possible at any time.
Scalability Limited by ETL server CPU/RAM. Scaling requires bigger (expensive) servers. Scales with the DWH compute cluster (elastic, pay-per-query in cloud DWHs).
Tooling SSIS, Informatica PowerCenter, Talend, Pentaho — legacy enterprise tools. dbt + Snowflake / BigQuery / Redshift. Modern default.
Use today? Legacy systems. Strict compliance scenarios where raw sensitive data (PII, PHI) cannot be stored in the DWH. Modern default for cloud data platforms. Cloud compute is cheap and elastic.

3. dbt (Data Build Tool) — Deep Dive

dbt is the modern standard transformation tool. Engineers write simple SELECT statements; dbt handles DDL, dependency resolution, testing, and documentation automatically.

dbt Feature What It Does
Models Each .sql file is a model. dbt compiles it into a CREATE TABLE AS or CREATE VIEW AS statement. Reference other models with {{ ref('model_name') }} — this builds the DAG automatically.
Materializations Control how a model is persisted: view (no storage, always computed), table (full rebuild each run), incremental (only process new/changed rows — critical for large tables), ephemeral (a CTE, not materialized at all).
DAG / Lineage Graph dbt infers the full dependency graph from ref() and source() calls. Executes models in the correct order. Visualized in the docs site.
Tests Schema tests run after every build: not_null, unique, accepted_values, relationships. Custom SQL tests and dbt-expectations package tests for advanced validation. Test failures can block downstream model execution.
Documentation Auto-generated HTML site with lineage graph, model descriptions, column-level descriptions, and test results. Serves as a living data catalog for dbt models.
Snapshots Built-in SCD Type 2 implementation. Define a snapshot with a strategy (timestamp or check) and dbt manages effective dates and the current flag automatically.
Macros Jinja-based reusable SQL templates. Write a macro once (e.g., a date-spine generator, a standardized column naming convention); reuse across hundreds of models.
Seeds Static CSV files (currency codes, country codes, status mappings) committed to the repo and loaded into the DWH as tables via dbt seed.
Sources Declare upstream raw tables (Bronze layer) with source(). Enables source freshness testing — dbt can alert if a Bronze table hasn't been updated in X hours.

4. CI/CD Pipeline for Data

  1. Developer pushes a feature branch with a new or modified dbt model / Airflow DAG.
  2. CI runs automatically on PR: dbt compile (validate SQL syntax), sqlfluff lint (enforce SQL style), dbt build --select state:modified+ (build only changed models and their children against a dev schema), run all tests.
  3. Peer review of the diff + CI results.
  4. Merge to main triggers CD: auto-deploy to QA environment, run full test suite, promote to PROD on success.
  5. Rollback strategy: Because Bronze is append-only and Gold models are rebuilt from Silver/Bronze SQL, a broken Gold model can be rolled back by reverting the dbt code and rebuilding — no point-in-time database restore needed.

Deep Dive: Data Products

A Data Product is the deliberate packaging of Gold layer data as a reliable, governed, consumer-oriented asset — a fundamental shift from "data as a pipeline byproduct" to "data as a managed product with an owner, SLA, and support model."

Table vs. Data Product: A table is rows and columns. A Data Product is the table plus discoverability, ownership, quality guarantees, semantic documentation, versioning, and ongoing support — like a software product, but for data.

1. Types of Data Products

Type Description Consumer Example
Dataset / Table / View A clean, governed Snowflake table or secure view with documented schema and SLA. Data analysts, BI developers, other data teams. GOLD.FACT_SALES with daily SLA and column-level definitions.
Report / Dashboard A pre-built visualization published to a BI platform. Business users, executives. Monthly Revenue Dashboard. Daily Operations Report in Tableau.
Data API A REST or GraphQL endpoint serving data programmatically to applications. Application developers, microservices, external partners. Product Catalog API returning current pricing in JSON. Customer 360 lookup API.
ML Training Dataset A curated, versioned dataset with verified features and labels for model training. Data scientists, ML engineers. Customer Churn prediction dataset: 24 months of behavioral features with churn labels.
Feature Store Pre-computed, continuously updated feature vectors for low-latency model serving. ML models in production, real-time scoring services. Real-time fraud risk features updated every 5 minutes for the fraud scoring model.
Event Stream A governed, documented Kafka topic or Kinesis stream with schema registry. Downstream microservices, streaming analytics applications. Order Events Kafka topic consumed by 5 downstream services with Avro schema contract.

2. The 8 Characteristics of a Data Product

  1. Discoverable: Registered in a Data Catalog (Alation, Collibra, DataHub, Atlan). Indexed with business-friendly tags so any employee can find it with a keyword search — without asking the data team.
  2. Addressable: Has a unique, stable, permanent location — a Snowflake schema path, API endpoint, Kafka topic name, or S3 URI. These identifiers never change without a versioning & migration process.
  3. Trustworthy (SLAs): Backed by a Service Level Agreement. The owner formally commits to: "Updated by 8:00 AM daily. 99% data quality test pass rate. Incident response within 30 minutes."
  4. Self-Describing: The product contains its own metadata — column definitions, business glossary mappings, example queries, data dictionary. Consumers should never need to email the engineering team to understand what a column means.
  5. Interoperable: Uses global enterprise standards: ISO 8601 dates, ISO 4217 currency codes, shared customer / product master keys. Joinable with other Data Products without ambiguity or manual key mapping.
  6. Natively Accessible: Each consumer type gets their preferred interface — SQL analysts get a view, app developers get an API, data scientists get a pandas-ready notebook endpoint. No consumer should need to build a pipeline to access the product.
  7. Secure by Default: Row-level security, column-level masking for PII, and RBAC access controls are built into the product at creation time — not bolted on later. The default posture is deny; access is explicitly granted.
  8. Versioned: Breaking schema changes (column renames, type changes, column removals) are versioned (v1 → v2) with a deprecation notice and migration guide. Old versions remain available during a defined transition period.

3. SLA vs. SLO vs. SLI

Term Full Name What It Is Data Engineering Example
SLI Service Level Indicator The actual measured metric from the system. Measured: "Gold.Fact_Sales was last updated at 7:45 AM today."
SLO Service Level Objective The internal target for the SLI. If the SLI breaches the SLO, the team is alerted. Target: "Gold.Fact_Sales must be updated by 8:00 AM on 99% of business days."
SLA Service Level Agreement The formal, contractual commitment with consequences if breached. Usually set softer than the SLO to give internal buffer. Contract: "If Fact_Sales is not updated by 8:30 AM, the data team will notify Finance within 15 minutes and provide an ETA."

4. Data Contracts (Producer–Consumer)

A Data Contract is the binding schema and semantic agreement between a Data Product owner (producer) and its consumers. It is treated like a software API contract:

  • Schema Contract: Column names, types, and nullability are guaranteed stable. Changes require a versioned migration.
  • Semantic Contract: Business definitions are stable. "Net_Revenue" always means revenue after returns and discounts — not gross.
  • Quality Contract: Freshness, completeness, and accuracy SLOs are formally stated.
  • Breaking Change Policy: Any breaking change (column rename, type widening, removal) requires a minimum 30-day notice, a versioned transition path, and simultaneous availability of both old and new schemas.

5. Data Product Lifecycle

  1. Discover: Identify the business need. Who are the consumers? What decisions will this data enable? Is this product already built somewhere?
  2. Design: Define the Data Contract, schema, SLA, security model, and ownership before writing a single line of pipeline code.
  3. Build: Implement Bronze → Silver → Gold pipeline. Write data quality tests. Register in catalog with full documentation.
  4. Publish: Grant access to initial consumers. Set up monitoring and alerting. Announce availability.
  5. Operate: Monitor SLAs, respond to quality incidents, handle consumer support questions.
  6. Iterate: Add new columns, improve performance, or extend coverage based on consumer feedback. Non-breaking changes only — new columns are backward-compatible.
  7. Deprecate: Notify all consumers with a formal sunset date. Provide a migration guide to the replacement product. Remove access only after the sunset date passes.

Governance & Data Trust

Data Governance is the framework of policies, processes, and accountabilities that prevents a Data Lakehouse from becoming a Data Swamp — where data is present but untrustworthy, undefined, or inaccessible to the right people.

1. Data Classification Levels

Classification Description Examples Required Controls
Public Freely shareable with anyone, including external parties. Product catalog, public pricing, press releases. None beyond standard web access controls.
Internal For employees only. Not for external sharing. Internal reports, org charts, project documentation. Basic authentication. Not shared outside the company.
Confidential Sensitive business information with limited internal distribution. Financial forecasts, M&A plans, contract values, customer lists. RBAC. Audit logging. Need-to-know access.
PII Personally Identifiable Information — can identify a specific individual. Full name, email, phone, SSN, passport number, IP address, device ID, precise location. Masking / tokenization in non-production. GDPR / CCPA right-to-deletion. Access audit logs. Column-level security.
PHI Protected Health Information — health data linked to an individual. Diagnoses, prescriptions, medical record numbers, insurance information. HIPAA compliance. Encryption at rest and in transit. BAA required for processors. Strict audit logging.
PCI Payment Card Industry data — credit card and cardholder data. Card numbers, CVV, expiration dates, cardholder names. PCI-DSS compliance. Tokenization mandatory. No storage of CVV after authorization. Quarterly vulnerability scans.

2. RBAC vs. ABAC

Model Description Example Best For
RBAC
(Role-Based Access Control)		 Access is granted to roles; users are assigned roles. All users in a role get identical permissions. Users in the FINANCE_ANALYST role can SELECT on all Finance Gold tables. No one else can. Most enterprises. Simple to implement, audit, and explain to regulators.
ABAC
(Attribute-Based Access Control)		 Access controlled by attributes of the user, the data, and the environment — evaluated dynamically at query time. A US-region analyst can only see customer records WHERE customer.region = user.region. A European user cannot see US PII even in the same role. Regulated industries (healthcare, banking). Multi-regional companies with geographic data residency requirements.
Snowflake implementation: RBAC is native (grants on roles). ABAC is implemented via Row Access Policies (row-level filtering) and Dynamic Data Masking (column-level masking) — both evaluated at query runtime.

3. Data Masking Techniques

Technique Description Reversible? Example
Static Masking Replace PII with a fixed mask character. Permanent data transformation — used in non-production environments. No john.doe@company.com → ***@***.***
Dynamic Masking Masking applied at query time based on the calling role — underlying data unchanged in storage. Different roles see different views of the same column. N/A (data unchanged) Analyst role sees ***@***.***. Admin role sees john.doe@company.com. Same Snowflake column, different output per role.
Pseudonymization Replace PII with a consistent but opaque token. The same real value always maps to the same pseudonym — enabling analytics without exposing PII. Yes (with mapping table, strictly controlled) John Doe → CUST_8472. Aggregations still work; individual identity is hidden.
Tokenization Replace sensitive values with random tokens. A secure, separate vault maps tokens back to real values. Token is meaningless without the vault. Yes (vault access required) Credit card 4111-1111-1111-1111 → TKN-9F2A-3B41. Only the payment processor's vault system can reverse it.
Generalization Replace a specific value with a less precise range or category — reduces re-identification risk in aggregate datasets. No Age 34 → 30–39. ZIP code 90210 → 902**. Salary $87,500 → $80K–$100K.

5. The Data Catalog Ecosystem

Concept Definition Example
Technical Metadata Physical, machine-readable properties of the data. user_id VARCHAR(50) NOT NULL stored in GOLD.DIM_CUSTOMER, last updated 2026-06-08 07:45 UTC, 4.2M rows.

6. Master Data Management (MDM)

MDM creates a single, authoritative "golden record" for critical shared enterprise entities — eliminating the ambiguity that arises when the same real-world entity is represented differently across multiple source systems.

  • Problem: Salesforce stores "RSI International." SAP stores "RSI International, Inc." Workday stores "RSI." These are the same company — but joining them produces 3× duplicate revenue figures.
  • MDM Solution: A matching and merging process (probabilistic or deterministic) creates one master record with a Golden Customer ID that all other systems reference.
  • Common MDM Domains: Customer MDM, Product / Item MDM, Vendor / Supplier MDM, Employee MDM, Location MDM.
  • Styles: Registry (MDM maintains mapping but data stays in source), Consolidation (MDM reads all sources, creates read-only golden record), Coexistence (MDM pushes golden key back to all systems), Centralized (single system of record).

7. Schema Registry & Evolution

When using event streaming (Kafka) with structured formats (Avro, Protobuf), a Schema Registry stores and enforces the schema of every topic:

  • Producers serialize messages against the registered schema — invalid messages are rejected before landing in Kafka.
  • Consumers deserialize using the same registered schema — no field-by-field guessing.
  • Compatibility modes: Backward (new schema can read old data), Forward (old schema can read new data), Full (both). Critical for managing schema changes without downtime.
  • Popular tools: Confluent Schema Registry, AWS Glue Schema Registry.

8. Data Retention & Storage Tiers

  • Define a data retention policy for each classification level: GDPR may require deletion of PII after its purpose expires; SOX may require financial records for 7 years.
  • Automate lifecycle transitions: move data from Snowflake (Hot) → S3 Standard-IA (Warm) → S3 Glacier (Cold) as it ages, using S3 Lifecycle Policies or Snowflake Data Retention settings.
  • Maintain a data inventory: know exactly what PII you hold, where it is, and when each record's retention period expires — required by GDPR Article 30.

Data Quality & Observability

Reliable Data Products require continuous, automated validation and monitoring. Data Quality defines the rules that data must conform to. Data Observability continuously monitors production data to detect when reality diverges from those rules — automatically, in real time.

Key distinction: Data Quality tests are deterministic rules ("this column must be not-null"). Data Observability is ML-driven anomaly detection ("this column's null rate suddenly spiked from 1% to 35% — that's unusual relative to its 30-day history"). You need both.

1. The 7 Dimensions of Data Quality

Completeness

Are all expected records and fields present? Are we missing rows? Are mandatory columns populated? Example: customer_email should be populated on 98%+ of rows.

Accuracy

Does the data correctly represent the real-world entity? Is the value true? Example: Does the revenue figure in Gold match the source ERP system's own ledger?

Consistency

Is the same data represented identically across systems and tables? Does the same fact contradict itself? Example: "John Smith" in Salesforce vs. "John Smyth" in SAP — same person, different spelling.

Timeliness (Freshness)

Is data available when consumers need it? Is it current enough to make decisions? Example: The daily sales table must be updated before the 8:00 AM business review.

Uniqueness

Are there no unintended duplicate records? Does each entity appear exactly once? Example: ORDER_ID must appear exactly once in Fact_Orders — duplicates inflate revenue metrics.

Validity

Does data conform to the defined format, range, and business rules? Is the value in the acceptable domain? Example: order_status must be one of ('OPEN','SHIPPED','CLOSED','CANCELLED').

Integrity

Are referential relationships intact across tables? Are foreign keys valid? Example: Every customer_id in Fact_Sales must exist in Dim_Customer — orphaned keys indicate broken joins.

2. The Data Testing Pyramid

Level Test Type What It Checks Example
Level 1 (Base) Schema Tests Column names, data types, not-null constraints, primary key uniqueness. order_id is unique and not null. revenue is a DECIMAL type.
Level 2 Row-Level Value Tests Accepted value lists, range checks, format validation via regex. status ∈ ('OPEN','CLOSED'). amount ≥ 0. email matches regex ^[^@]+@[^@]+\.[^@]+$.
Level 3 Referential Integrity Tests Foreign keys in fact tables must have matching rows in dimension tables. Every product_id in Fact_Sales must exist in Dim_Product. Every customer_id must exist in Dim_Customer.
Level 4 Business Rule Tests Custom domain logic that reflects actual business definitions and constraints. Revenue for CANCELLED orders must be 0 or negative (refund). Total invoice line items must sum to the invoice header total within ±$0.01. Shipped_Date must be ≥ Order_Date.
Level 5 (Top) Cross-Dataset / Reconciliation Tests Aggregate comparisons across pipeline layers or against external ground-truth systems. Row count in Silver must equal Bronze (zero data loss). Total Gold revenue must match the finance system ledger within 0.01%. Daily loaded row count must be within ±20% of the 30-day rolling average.

3. dbt Built-In Tests

dbt ships with four schema tests applicable to any column in schema.yml:

  • not_null — No NULL values in the column.
  • unique — No duplicate values in the column.
  • accepted_values — All values belong to a specified list.
  • relationships — Foreign key column references a valid row in another model.

The dbt-utils and dbt-expectations packages extend this with advanced tests: row count thresholds, distribution checks, regex validation, cardinality checks, and column-value comparison across models.

4. The 5 Pillars of Data Observability

Observability goes beyond static rule tests — it continuously monitors production data for unexpected changes, even when no code was deployed. ML-based anomaly detection identifies issues that static thresholds miss.

1. Freshness

Is data being updated at the expected frequency?

Alert if Fact_Sales hasn't received new rows in 26 hours when its normal cadence is every 24 hours. Staleness is often the first signal that an upstream pipeline has silently failed.

2. Volume

Is the row count within expected bounds?

Alert if today's ingestion loaded 50% fewer rows than the 30-day average — likely a source system issue, a dropped partition, or a pipeline filter bug. Also alert on unexpected volume spikes.

3. Schema

Has the table structure changed unexpectedly?

Alert if a column was dropped, renamed, or had its data type changed by an upstream source team — without going through the agreed Data Contract change process.

4. Distribution

Have the statistical properties of column values shifted unexpectedly?

Alert if the average order_value suddenly drops by 40% — may indicate a currency conversion bug, a timezone misalignment, or a new product category with $0 prices.

5. Lineage

When an issue is detected, what caused it and what is affected?

Column-level lineage shows exactly which upstream transformation introduced the anomaly, and which downstream dashboards and Data Products are now serving bad data. Enables instant scope-of-impact assessment.

6. Circuit Breakers & Quality Gates

A Circuit Breaker halts a pipeline automatically when data quality falls below a threshold — preventing bad data from propagating to Gold layer tables, dashboards, and business decisions.

Hard Stop (Circuit Breaker)

Pipeline fails immediately. No data is written to the next layer. Alerts are sent to the data team and stakeholders. Used when bad data would be catastrophically misleading — financial reporting, regulatory submissions.

Soft Stop (Warn + Continue)

Pipeline continues but logs a warning and sends an alert to the data steward. Used for non-critical anomalies where partial or slightly degraded data is better than no data.

Quarantine Pattern

Failing rows are routed to a _QUARANTINE table instead of being dropped. The main pipeline continues with clean rows. Quarantined rows are investigated and reprocessed (or discarded) after review.

7. SLA Monitoring & Incident Management

  • Define a data SLA for every Data Product: "Updated by 7:00 AM daily on 99.5% of business days."
  • Implement automated SLA monitoring in your orchestration tool (Airflow SLA callbacks) or observability platform — fire alerts before business users notice.
  • Maintain an SLA breach log. Track Mean Time to Detection (MTTD) and Mean Time to Resolution (MTTR) for data incidents. Trend these metrics over time to surface chronically unreliable pipelines.
  • Establish an incident runbook: who is the on-call for a given Data Product? What is the escalation path? How is the impact communicated to downstream consumers?
  • Conduct blameless post-mortems on significant incidents — focus on process and system improvements, not individual fault. Document the root cause and preventive measures in a shared incident log.
