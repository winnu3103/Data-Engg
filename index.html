Enterprise Data Engineering Concepts & Architecture

A comprehensive reference guide for modern data architecture, modeling, and governance.

The Medallion Architecture & Data Layers

The Medallion architecture organizes data logically as it flows from raw source systems to business-ready assets. The general rule is: Normalize for integrity (left) and denormalize for performance/usability (right).

Standard Flow vs. Custom Enterprise Flow

In a mature enterprise pipeline, the physical implementation expands to include operational stops:

  • Bronze (STG): Landing zone. Ingests raw data from multiple sources with no changes.
  • Bronze (ODS - Operational Data Store): Deduplicates staging data based on key columns and last modified times to capture the latest operational state via upserts.
  • Silver (CDM - Common Data Model): The Conformed Domain Layer. Data is normalized and aligned to enterprise domains. It holds the current state and acts as the "Single Source of Truth" for operational analytics.
  • Gold (Core/Historical): The Dimensional Model. Denormalized into Facts and Dimensions. History is captured here using SCD Type 1 (Facts) and SCD Type 2 (Dims).
  • Gold (Data Products): Decoupled, highly aggregated tables or views designed for specific business users to self-serve.
What is an "Operational Purpose" in the Data Warehouse?
It refers to Operational Analytics, not high-speed application transactions. The CDM layer integrates disparate source systems (e.g., Salesforce, Zendesk) to create unified metrics that can be fed back into business applications via Reverse ETL.

Dimensional Modeling (Star Schema)

The core philosophy of dimensional modeling is separating the quantitative metrics from the descriptive context to enable high-performance analytics.

Facts vs. Dimensions

Feature Fact Tables (The Numbers) Dimension Tables (The Context)
Purpose To record the measurement of an event. To provide the "Who, What, Where, When".
Structure Contains foreign keys and numeric metrics (Price, Quantity). Contains primary keys and descriptive text attributes.
Data Volume Massive (Billions of rows). Small to medium.

The Grain

The "Grain" is the fundamental starting point of any dimensional design. It represents the atomic level of detail stored in your fact table (e.g., "One row per line item on a receipt"). Defining the grain dictates what dimensions can be attached and guarantees query accuracy.

Real Transactional Data vs. Fact Tables

Transactional data (OLTP) is highly normalized to write data safely and fast. Fact tables (OLAP) are denormalized for reading data quickly. You separate Facts from Dims to prevent massive storage bloat and to handle Slowly Changing Dimensions (SCDs) efficiently without updating billions of rows.

Data Vault 2.0 vs. Star Schema

There is often confusion between a centralized enterprise repository and a true Data Vault. They solve different problems.

The Data Vault Architecture

A Data Vault is an agile, insert-only methodology typically placed in the Silver layer to handle extreme structural changes from upstream systems without breaking the warehouse.

  • Hubs: Represent core business entities. They contain only the unique Business Key (e.g., Customer ID).
  • Links: Represent relationships or transactions between Hubs.
  • Satellites: Hold all descriptive context and history. They are insert-only to provide an auditor-grade history.

Why a Star Schema with SCD Type 2 is NOT a Data Vault

If your architecture deduplicates in the ODS, keeps only the current state in the CDM, and captures history in the Gold Core via SCD Type 2 Dimensions, you are running a Kimball Dimensional Model, not a Data Vault.

This is highly effective: it keeps the Silver layer lightweight and passes historical tracking to the Gold layer where analytical queries actually require it.

Aggregated Tables vs. Data Products

In the Gold layer, an aggregated table and a data product might look identical in the database, but they serve completely different operational scopes.

  • Aggregated Table: A technical asset designed to optimize query performance (e.g., pre-summing rows). It requires technical intervention and joins to be fully utilized.
  • Data Product: A philosophical shift. It is a self-contained asset tailored for business users. It requires zero technical joins (often a "One Big Table" or OBT) and includes metadata, SLAs, and Data Contracts.

Guaranteeing Trust (Data Contracts & Orchestration)

To ensure a Data Product refreshes accurately, you cannot rely on scheduled clock times. You must use:

  1. Sensor-Based Orchestration (Airflow/Dagster): Downstream layers only execute upon receiving a success signal from upstream layers.
  2. Data Contracts: Agreements with software developers that source schemas will not change without warning.

Data Mesh & Organizational Decentralization

Data Mesh is a decentralized socio-technical approach. It shifts data away from monolithic, centralized IT teams and gives ownership back to the business domains.

Centralized vs. Decentralized

  • Centralized: One data team manages all pipelines. Pros: Consistency. Cons: Becomes a massive bottleneck; engineers lack business context.
  • Decentralized: Individual business domains (Sales, Finance) build their own pipelines. Pros: Speed and deep business alignment. Cons: Requires strict governance to avoid chaos.

The 4 Pillars of Data Mesh

  1. Domain-Driven Ownership: The people closest to the data own the pipelines.
  2. Data as a Product: Domains serve clean, reliable data to the rest of the company.
  3. Self-Serve Data Platform: A central IT team provides the automated infrastructure so domains don't have to build servers from scratch.
  4. Federated Computational Governance: Global standards are automated into the platform to ensure domain data can interoperate securely.

Data Governance, Semantics & Catalogs

A Data Catalog is the "Google for your company's data," acting as a centralized portal that combines several distinct pillars of governance.

Pillar Definition The Question it Answers
Technical Metadata The physical structure (column types, tables). "What is the shape of the data?"
Data Dictionary Technical descriptions of a specific database. "What is inside this specific table?"
Business Glossary Human-language definitions of company terms. "What do we define as an 'Active Customer'?"
Semantics The underlying business logic and translation. "How is this metric calculated?"
Data Lineage The visual map of data movement. "Where did this data come from (Bronze -> Gold)?"
The Power of Semantics: Embedding semantics in the CDM/Silver layer ensures that business rules (like filtering out test accounts for revenue calculations) are coded once, establishing a single source of truth that flows reliably into all downstream Data Products.

The Data Engineering Knowledge Pyramid

Understanding where these concepts fit helps structure your career development and daily engineering habits.

  • Tier 1: Infrastructure (The "How"): Row vs. Columnar, ACID, Compute/Storage separation. Level: Master/Hands-On.
  • Tier 2: Architecture & Modeling (The "What"): Medallion layers, Star Schemas, SCD Type 2. Level: Fluent/Architectural.
  • Tier 3: Governance & Strategy (The "Why"): Data Mesh, Data Products, Semantics, Centralized vs. Decentralized. Level: Aware/Strategic.

Practical Daily Application

  1. Audit Strategy: Use row-level hashing in your Gold tables to quickly identify logic breaks during SCD Type 2 merges.
  2. Hard-Code Semantics Left: Stop writing repeated `CASE WHEN` logic in Gold. Build semantically valid flags in the CDM layer.
  3. Self-Documenting Workflow: Use your commit messages and dbt documentation to define the Semantics and Glossary Terms, not just the technical changes.
