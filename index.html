The Complete Data Engineering Lifecycle

A Data Engineer must understand the end-to-end journey of data — from its birth in a source system to its eventual archival. Every stage introduces risk; missing or mishandling any stage contributes to what is known as a Data Swamp.

Key Principle — Data as a Product: Data should be treated as a first-class asset at every stage: discoverable, trustworthy, governed, and well-understood — not just present in a table.
Stage 1 · Data Generation
Data originates from source systems. Types of sources:
  • OLTP Databases: ERP (SAP), CRM (Salesforce), e-commerce backends — high-frequency transactional writes.
  • IoT & Sensors: Machine telemetry, GPS, environmental sensors — high-volume, continuous streams.
  • SaaS APIs: REST / GraphQL APIs from third-party platforms (Hubspot, Stripe, Workday).
  • Event Streams: Clickstreams, user-behavior events published to message brokers.
  • Files: CSV uploads, EDI feeds, PDF exports, flat-file drops on SFTP.
Data formats: Structured (rows & columns) Semi-structured (JSON / XML / Avro) Unstructured (images / video / free text)
Stage 2 · Data Ingestion (Extract / Load)
Data is moved from sources into the data platform. Four main patterns:
  • Full Batch: Entire source table extracted on each run. Simple, but expensive at scale.
  • Incremental Batch: Only rows changed since the last run (using a watermark column). Far more efficient for large tables.
  • Streaming: Events flow in real-time via message brokers (Kafka, Kinesis). Millisecond latency, higher operational complexity.
  • CDC (Change Data Capture): Captures only INSERT / UPDATE / DELETE operations from the source system's transaction log — the gold standard for efficiency and completeness. See Tab 7 for a deep dive.
Stage 3 · Raw Storage (Landing Zone)
Data lands in a raw storage zone — a Data Lake (S3 / ADLS / GCS), a staging database, or an object store. The core rule: get it in, unchanged. File format choices (Parquet, Avro, JSON) made here have downstream performance and cost consequences. See Tab 2 for formats.
Stage 4 · Data Profiling & Discovery
Before building transformations, engineers statistically profile the data to understand its true state — not how it should look, but how it actually looks:
  • What percentage of each column is NULL?
  • What are the min / max / average values of numeric fields?
  • Are there duplicate rows based on a business key?
  • Do referential integrity constraints hold between tables?
  • Are there anomalous string lengths or outlier values?
Building pipelines without profiling is one of the most expensive mistakes in data engineering — assumptions made here haunt pipelines for years.
Stage 5 · Transformation & Processing (ELT / ETL)
Raw data is cleaned, standardized, enriched, and joined. Business rules (semantics) are applied here: deduplication, null handling, type casting, currency normalization, timezone standardization, code-table mapping. This is the ELT step in a modern Data Lakehouse (transform inside the warehouse using SQL / dbt).
Stage 6 · Data Modeling
Transformed data is restructured into a formal analytical model — Star Schema, Data Vault, 3NF, or One Big Table — optimized for the query patterns of its consumers. The model determines query speed, ease of understanding, and how well the data can answer historical questions. See Tabs 3–6.
Stage 7 · Orchestration & Scheduling
A pipeline scheduler (Apache Airflow, Prefect, Dagster) coordinates execution: ensuring Stage 5 does not run before Stage 4 completes, handling failures gracefully, retrying on transient errors, and sending SLA-breach alerts. Without orchestration, pipelines break silently — no one knows. See Tab 8.
Stage 8 · Serving & Data Products
Clean, modeled data is exposed to consumers as dashboards (Tableau, Power BI), SQL views, REST APIs, or ML training datasets. In a modern Data Mesh, these are packaged as formal Data Products with documented SLAs, ownership, and quality guarantees. See Tab 10.
Stage 9 · Data Quality & Observability (Continuous)
Automated testing and monitoring run on every pipeline execution to detect freshness failures, volume anomalies, schema changes, and accuracy degradation — before business users notice. This is not a one-time activity; it runs perpetually in production. See Tab 12.
Stage 10 · Governance, Compliance & Archiving
Tracking data lineage (where data came from and where it went), enforcing role-based access control (RBAC), applying classification labels (PII, PHI, PCI), ensuring regulatory compliance (GDPR, CCPA, HIPAA), and archiving cold data to cheaper storage tiers to reduce cost. See Tab 11.

The Data Contract — The Glue Between Stages

A Data Contract is a formal, versioned agreement between a data producer (the team generating data) and a data consumer (the team using it). It codifies:

  • Schema: Column names, data types, and nullability guarantees.
  • Semantics: What each field means in business terms.
  • SLA: Freshness guarantees — when data will be available and at what quality level.
  • Breaking Change Policy: How schema changes will be communicated, with advance notice and versioning.
Without Data Contracts: A source team can silently rename a column overnight and every downstream pipeline fails at midnight. Data Contracts are the contract-first discipline that prevents this class of failure entirely.

Storage & Database Foundations

1. Storage Types

Database (OLTP DB)

Organized storage for running applications. Row-based. Optimized for fast reads/writes of individual rows. Examples: PostgreSQL, MySQL, SQL Server, Oracle.

Data Warehouse (DWH)

Centralized repository for analytics and reporting. Columnar storage. Optimized for scanning millions of rows across few columns. Examples: Snowflake, BigQuery, Redshift.

Data Mart

A focused, department-specific subset of the Data Warehouse. Sales, Finance, and Marketing each get a purpose-built mart for faster, simpler queries scoped to their domain.

Data Lake

A vast pool of raw data in native formats (JSON, CSV, Parquet, images, video). Schema applied at query time ("schema on read"). Primary home for ML datasets and archival.

Data Lakehouse ⭐

A modern hybrid: raw files stored in a Data Lake (S3 / ADLS / GCS) but accessed with Data Warehouse capabilities — ACID transactions, SQL, indexing, schema enforcement — via open table formats (Delta Lake, Apache Iceberg).

Operational Data Store (ODS)

A near-real-time integration layer holding the current state of operational data integrated from multiple source systems. Designed for current-state queries, not deep historical analytics.

2. Row-Oriented vs. Columnar Storage

Dimension Row-Oriented (OLTP) Columnar (OLAP)
Physical layout All columns of one row are stored together on disk: (id=1, name='Alice', age=30) → (id=2, name='Bob', age=25) Each column stored together: all IDs, then all names, then all ages
Best for Reading or writing a single row quickly. INSERT / UPDATE / DELETE transactions. Aggregating a single column across millions of rows: SELECT SUM(revenue) …
Compression Poor — each "chunk" is heterogeneous (mixed types), compresses badly. Excellent — homogeneous column data (all integers, all dates) compresses 5–10×.
I/O efficiency Must read every column even if only one is needed. Only reads columns referenced in the query — "column pruning."
Examples PostgreSQL, MySQL, Oracle, SQL Server Snowflake, BigQuery, Redshift, Apache Parquet files

3. OLTP vs. OLAP vs. HTAP

Feature OLTP (Online Transaction Processing) OLAP (Online Analytical Processing) HTAP (Hybrid)
Purpose Run the business (app backends, e-commerce) Analyze the business (BI, dashboards, reporting) Both simultaneously on one platform
Query types Fast, simple INSERT / UPDATE / DELETE Complex SELECT with massive aggregations & JOINs Mix of transactional and analytical
Row count per query 1–100 rows Millions–billions of rows Both extremes
Concurrency Thousands of short concurrent transactions Handful of long-running analytical queries Manages both workloads
Examples PostgreSQL, MySQL, Oracle Snowflake, BigQuery, Redshift SingleStore, TiDB, Snowflake Unistore
